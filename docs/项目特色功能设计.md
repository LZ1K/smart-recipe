# Smart Recipe 智能菜谱助手 — 项目特色功能设计

---

## 1. 目标人群画像

**谁在用？**

核心用户是 25-40 岁的城市家庭做饭人。ta 不是专业厨师，但需要每天为家人做一两顿饭。典型场景是：下班路上或者站在冰箱前，掏手机想找个菜谱——但不知道做什么、不知道冰箱里那几样食材能拼出什么、更不知道今天外面 39 度是不是该放弃开火的想法。

**痛点**：

- 菜谱 App 千人一面，永远推那几道热门菜，跟你无关
- 通用 AI 助手记不住你的口味，每次都要重新说一遍"我不吃香菜"
- 没有任何菜谱工具会告诉你"今天太热了，别做红烧肉了，做个凉拌菜吧"
- 更不会有工具告诉你"白菜现在正当季便宜，多买点"

---

## 2. 通用助手的不足

如果把这个问题丢给 ChatGPT 或者通用的 AI 助手，表面上它能推荐菜谱，但深层次的问题一个都解决不了：

**记不住你**。通用助手每次对话都是独立的，你上次说过不吃香菜，下次换个对话它又推荐香菜拌牛肉。它没有一个持久化的偏好模型，更不会区分"不爱辣味"跟"不吃辣椒"——你随口说一句"不太能吃辣"，它可能从此再也不推青椒炒肉丝，而青椒根本不辣。

**感知不了外部世界**。通用助手不知道外面几度、不知道现在什么菜便宜、不知道这个月什么食材正当季。它的推荐完全脱离物理现实——39°C 高温天照样推火锅，冬天照样推凉拌黄瓜。你让它推荐"适合今天的菜"，它只能猜。

**不会追问**。你说不吃辣椒，它不会反问"那青椒和甜椒吃吗"。它不理解食材之间有关联但不相等的关系——辣椒是辣的，青椒不辣，但它们都属于辣椒类。一刀切式的理解导致用户被过度排除，错过大量本该能吃到的菜。

**推荐无依据**。通用 AI 的推荐排序基本靠模型内部权重，没有天气权重、季节权重、价格权重这些外部的、可解释的决策因子。它告诉你"推荐番茄炒蛋"，但不会告诉你为什么——因为今天热、番茄当季、你喜欢酸甜口。

## 3. 特色功能设计：多维度实时驱动的菜谱推荐引擎

Smart Recipe 的推荐不是静态标签匹配，而是**天气 × 菜价 × 季节 × 口味偏好 × 食材喜恶**五个维度的实时决策。下面以"天气驱动推荐"为例展开完整设计。

### 3.1 业务流程

```
用户打开聊天页
    │
    ├─→ 前端自动请求 GET /api/external-data/weather（默认城市：北京）
    │
    ▼
┌─────────────────────────────────────────────────┐
│             getWeather() 四级降级获取             │
│                                                  │
│  L1: wttr.in API 实时拉取  ──成功──→ source="api" │
│    │失败                                         │
│  L2: DB 读 WeatherRecord（24h内缓存）──成功──→ "cache" │
│    │过期                                         │
│  L3: 根据当月 + 城市纬度推算气温         ──成功──→ "seasonal_estimate" │
│    │失败                                         │
│  L4: 返回默认值（22°C / 50% 湿度）                │
└─────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────┐
│          detectWeatherAnomalies() 异常检测         │
│                                                  │
│  temp ≥ 38°C     → level: danger, type: extreme_heat  │
│  32°C ≤ temp < 38 → level: warning, type: high_temp   │
│  temp ≤ 0°C       → level: danger, type: extreme_cold  │
│  0°C < temp ≤ 10  → level: warning, type: low_temp     │
│  humidity ≥ 70%   → level: warning, type: high_humidity │
│  其他             → level: normal                       │
└─────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────┐
│       generateWeatherAdjustments() 建议调整        │
│                                                  │
│  高温(≥32°C):                                    │
│    boostedTags:    [清淡, 凉拌, 快手, 低脂]        │
│    suppressedTags: [暖身, 冬季, 辣的]              │
│                                                  │
│  低温(≤10°C):                                    │
│    boostedTags:    [暖身, 冬季, 炖煮, 下饭]        │
│    suppressedTags: [凉拌, 清淡, 冷菜]              │
│                                                  │
│  高湿(≥70%):                                     │
│    boostedTags:    [汤羹, 暖身, 微辣]              │
│    notice: "湿度较高，注意干货密封保存"              │
└─────────────────────────────────────────────────┘
    │
    ▼
API 返回 JSON（天气数据 + 异常检测结果 + 推荐调整 + 湿度提示）
    │
    ▼
前端 WeatherCard 组件渲染 → 用户看到实时天气 + 烹饪建议
    │
    ▼
用户发消息 → /api/chat 中 system prompt 包含天气调整策略
    → AI 回复自动避开 suppressedTags，倾向 boostedTags
```

### 3.2 核心逻辑

**为什么需要四级降级？**

wttr.in 是免费 API，无 SLA 保证。用户可能在地铁里网络抖动，也可能 API 临时挂了。如果每次都直接调 API 失败就显示"天气不可用"，体验很差。四级降级保证**只要 App 能打开，天气卡片就永远有数据显示**——最差情况下用默认值，用户无感知。

**为什么用标签加权而不是硬规则？**

如果高温天直接屏蔽所有含"辣"标签的菜，会误杀宫保鸡丁（微辣）这类高温天其实可以吃的菜。用 boostedTags / suppressedTags 做**软加权**，AI 在推荐时倾向于清淡菜但不强制排除，给用户留余地。

### 3.3 关键数据

**WeatherRecord 表**（Prisma Schema）：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String (cuid) | 主键 |
| city | String | 城市，默认"北京" |
| temperature | Float | 气温（°C） |
| humidity | Int | 湿度（%） |
| condition | String | 天气状况描述 |
| windSpeed | Float | 风速（km/h） |
| fetchedAt | DateTime | 数据获取时间 |
| source | String? | 数据来源标记（api/cache/seasonal_estimate） |
| anomalyLevel | String? | 异常等级（normal/warning/danger） |
| anomalyType | String? | 异常类型（extreme_heat/high_temp/extreme_cold/low_temp/high_humidity） |

**SeasonalIngredient 表**：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String (cuid) | 主键 |
| name | String | 食材名 |
| month | Int | 月份 1-12 |
| season | String | 所属季节 |
| price | Float | 当月均价（元/斤） |
| lastMonthPrice | Float? | 上月均价（用于涨跌计算） |
| priceChangePercent | Float? | 价格变化率（%） |
| priceAlert | String? | 价格预警（price_spike/price_drop） |

**季节推荐维度**（硬编码在 `src/lib/seasonal-data.ts`）：

| 季节 | 月份 | 当季食材 | 优先推荐分类 |
|------|------|----------|-------------|
| 春季 | 3-5 | 春笋、韭菜、菠菜、荠菜、豌豆 | 素菜、家常菜 |
| 夏季 | 6-8 | 冬瓜、苦瓜、黄瓜、番茄、丝瓜 | 素菜、汤羹 |
| 秋季 | 9-11 | 莲藕、山药、南瓜、螃蟹、板栗 | 汤羹、荤菜 |
| 冬季 | 12-2 | 白菜、萝卜、羊肉、山药 | 荤菜、汤羹、家常菜 |

## 5. 与项目其他功能的衔接

**与对话系统的衔接**：天气调整策略和季节推荐不是独立展示的，而是注入到 `/api/chat` 的 system prompt 中。AI 在生成回复时，已经知道了外面的天气、当季的食材、用户的口味偏好——不需要用户额外提问。用户说一句"推荐个菜"，AI 给出的回复背后是五个维度的综合：天气（热）→ 避开暖身标签 → 季节（6月）→ 倾向素菜汤羹 → 偏好（爱酸甜不爱辣）→ 优先番茄炒蛋/糖醋排骨 → 价格（番茄降价）→ 强调番茄划算。

**与偏好记忆的衔接**：对话中提取的偏好（`UserPreference`）在下一次对话加载时自动拼入 system prompt。这意味着偏好学习和天气推荐不是两套独立系统——用户说"我不吃辣"，AI 在高温天推荐清淡菜时，会避开带辣标签的清淡菜（如凉拌麻辣鸡丝），推真正匹配的（如凉拌黄瓜）。

**与食材关联知识库的衔接**：`Ingredient` 表存储了食材间的别名和关联关系（辣椒 → 青椒/甜椒/辣椒面）。当用户表达忌口时，AI 不直接一刀切，而是根据关联图谱追问。这个追问逻辑既在 system prompt 的规则里，也有 Ingredient 表做数据支撑——未来可扩展为自动查询关联食材而非硬编码规则。
